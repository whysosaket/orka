# Automatic and selected sharing

Project category settings control automatic synchronization on each Mac. `true` means Share automatically; `false` means Only when asked. Existing boolean values remain valid. New create/join flows default to automatic memories, skills, and plans, with sessions and ENVs off. Existing project settings, legacy projects without saved settings, and disconnected project catalogs preserve their previous behavior.

There are no per-resource sharing controls in the desktop. The installed plugin provides an explicit one-off workflow for local memories and instruction files, full skills, native sessions, and plans, including embedded plans. The private discovery catalog is separate from shared resources and review drafts. Discovery uses the existing source scoping, filesystem guards, complete session/lineage reader, and secret-file exclusions; it does not queue uploads or enable a category.

The local MCP server is the Orka executable's `--orka-plugin` command. It exposes metadata discovery, a snapshot preview, and selected publication. The remote sharing workflow does not read private local files. Plugin 0.3.0 additionally exposes shared-resource operations with separate read/write/manage OAuth consent; see the [plugin guide](../plugins/orka/README.md). Each local call must match the remote account and service origin, and the project must be active on this Mac. A current native session ID is preferred; ambiguous titles or recency require an explicit selection.

A preview stores exact cached blob references with a ten-minute token, account, service, project, source, and connected-folder identity. Publication consumes that snapshot rather than rereading a growing conversation. Its durable request ID depends on the resource and base revision. The queue authorizes only that exact payload, survives offline retries, and never grants automatic permission for later snapshots. Category changes do not turn a selected request into a broad grant.

Before sending any selected blobs, the native client checks the service's `selectedSharing: 1` capability and registers its existing device identity. `POST /v2/sharing/selected` accepts the existing v2 change schema. It uses ordinary publish authorization and conflict detection, or the existing immutable review-request path when suggestion is permitted. Membership, category/resource access, source audiences, provenance, and session ownership remain enforced by the shared core. Approval-required and conflicted results are not publication success.

Selected sharing uses the existing v2 change wire schema and encrypted ENV format, without deployment variable changes. The native cache adds an isolated local catalog table. The backend endpoint and capability are shared by OSS and managed composition roots; existing servers keep their prior behavior and must be updated before selected publication can complete. Older read-only plugins continue to work. This change does not deploy the service or replace installed desktop binaries.

## Verification and rollout

The local acceptance test runs the built native MCP executable against an isolated PostgreSQL/API fixture. It verifies discovery with all automatic categories off, a frozen session share, exact retries, a second explicit update, preservation of the original snapshot and native file, and unchanged sharing preferences. Backend HTTP tests cover all four categories, both hosting modes, membership removal, review requests, conflicts, forbidden ENV files, and retry identity. UI tests cover setup, settings, onboarding, keyboard interaction, and accessibility.

Codex accepts the desktop archive and loads both MCP servers; Claude Code validates it and inventories the workflow skills and two servers. These host checks do not claim a production publication. Packaging accepts an explicit executable path for a development build and defaults to the installed app path.

Roll out the shared backend first, then the updated desktop app and plugin 0.2.0. Remote `get_profile` must return the service origin and the API must advertise selected sharing. A client connected to an older service leaves the selected snapshot queued without uploading its blobs. Signed desktop installers, published plugin releases, and production deployment are separate release steps.
