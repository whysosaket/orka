# Desktop updates and recovery

## Install Orka

Quit Orka and drag **Orka** from the notarized DMG into Applications. Use the Applications folder in your home directory if your Mac restricts writes to the system Applications folder. Existing users install this first release over their previous Orka app. The app provisions its signed background updater on launch. Workspace and account data stay in Application Support and Keychain.

When a verified release is available, **Update available** appears in the sidebar across workspace tabs. Open it to review the version and release notes, then choose **Update and Restart** or **Later**. Orka prepares the approved build in the background and restarts when it is ready. If the desktop crashes before opening or repeatedly crashes after launch, the background updater presents Orka’s native repair prompt. It offers an approved forward update or an eligible previous version already on the Mac. An offline restore uses the latest withdrawal policy the Mac has seen.

## Build and promote a release

The [macOS build workflow](../.github/workflows/release.yml) produces a notarized DMG with one app and `Orka-update.zip` with the same stapled `Orka.app`. The updater is signed inside the bundle. The launcher provisions an independently signed copy under Application Support so it can keep running while Orka’s bundle is replaced. The installed copy persists across desktop releases with the same feed URL and trust key. Changes to the updater protocol, public key, or feed location require a compatible bootstrap release.

1. Provision a dedicated Ed25519 release policy signing key. Put the base64-encoded raw 32-byte public key in `ORKA_UPDATE_PUBLIC_KEY` in both protected environments. Set `ORKA_UPDATE_SIGNING_KEY` to the PKCS#8 PEM private key in `macos-update-publishing` only. Set its `APPLE_TEAM_ID` variable to the release signing team. The existing Apple signing credentials stay in `macos-signing`. Limit both environments to reviewed `main` workflows and keep access to the publishing key separate from Apple signing credentials.
2. Build the next version as **universal** and **notarized** from `main`. The release workflow uses Xcode 16.4 for the Intel and Apple Silicon launcher slices. Verify the DMG and the signed app with its nested updater, then attach the outputs to that version's GitHub desktop release. Publish the release for download. Keep each version and its update archive immutable.
3. Run **Publish macOS update policy** with **promote**, the version, and short release notes. The workflow verifies the notarized archive and its Apple team, then signs the policy and advances the `desktop-updates` branch. The default feed URL is `https://raw.githubusercontent.com/whysosaket/orka/desktop-updates/macos.json`. If `ORKA_UPDATE_FEED_URL` is overridden, the operator must serve the same signed policy at that URL. The feed works before sign-in and across managed and self-hosted instances.
4. The publishing workflow renews the 48-hour policy daily. Its environment must permit the scheduled `main` job to renew. If a reviewer gate is required for that environment, approve renewals before expiration. Monitor failed renewals and alert before the current policy expires.

## Withdraw a bad release

Run **Publish macOS update policy** with **withdraw** and the affected version. The withdrawal is permanent for that version. Optionally raise `minimum_version` when old builds must be excluded from installation and restore. The updater rechecks a fresh signed policy before an approved download can replace Orka. A Mac that has already observed a withdrawal remembers it across offline sessions. A Mac needs a successful feed refresh to learn about a new withdrawal.

Build the fix with a higher version and promote it. The updater can fetch it independently of the UI and sync process. Keep the old GitHub release for audit and mark it withdrawn in its release notes. Clients select from the signed desktop policy, including when the newest GitHub release is a server release.

## Data compatibility and acceptance

Increment [the desktop data epoch](../apps/mac/recovery/data-epoch) for a change that prevents the previous build from safely opening local data, retaining pending sync work, or using the supported server contract. The updater can install a forward version with a higher epoch and offers a local restore only within the same epoch. Test the old and new client against the same data and supported server versions before keeping the epoch unchanged.

The launcher preserves the LaunchServices PID and existing executable entry point when handing off to Tauri. The background updater records startup and exit health locally. For a regular update, it verifies the calling desktop process and rechecks the approved version and archive digest. The installer stages a signed full bundle on the installation volume, waits for foreground and background processes to release their shared runtime lock, and swaps the bundles atomically. An interruption leaves either the previous or the new complete bundle at the same path. The updater and application data live outside that swap.
