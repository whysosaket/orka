# Desktop updates and recovery

## Install Orka

Quit Orka and drag **Orka** from the notarized DMG into Applications. Use the Applications folder in your home directory if your Mac restricts writes to the system Applications folder. Existing users install this first release over their previous Orka app. The app provisions its signed background updater on launch. Workspace and account data stay in Application Support and Keychain.

When a verified release is available, its version appears in the sidebar across workspace tabs. In the collapsed sidebar, open the update icon to see it. Choose **Update and Restart**, open **View changelog** for the GitHub release, or close the card. Orka shows download percentage and a progress bar, then verification and restart status. Idle local plugin connections exit for maintenance; an active plugin request finishes before releasing the runtime lock. If the desktop crashes before opening or repeatedly crashes after launch, the background updater presents Orka’s native repair prompt. It offers an approved forward update or an eligible previous version already on the Mac. An offline restore uses the latest withdrawal policy the Mac has seen.

## Check for updates

Choose **Orka → Check for Updates…** in the macOS app menu, or open **Settings → Updates** under **This Mac** and choose **Check for Updates**. The menu opens Updates and starts a check immediately, including before sign-in in a separate Updates dialog. Existing Settings edits still use the Save, Discard, and Stay prompt before navigation. Checking does not install an update or restart Orka.

Updates shows the installed version, the result of the check, and the last successful check time. **Release notes** starts collapsed; expand it to read the verified release summary, or follow the changelog link to the full GitHub release. Notes remain available for the installed version when it is the release offered by the signed update feed. If a newer release is available, **Update and Restart** uses the same installer and progress as the sidebar. Check failures explain the problem and allow another check; a failed check does not report that Orka is up to date. Development builds without the packaged updater explain that updates are unavailable.

Orka also checks when the desktop opens and every four hours while it remains running. A manual check requests a fresh feed immediately. After a release is promoted to the update feed, an online, awake Mac normally sees it at the next launch or within four hours. Sleeping or being offline can delay detection. Publishing a GitHub release alone does not make it available to the updater; promotion is a separate step below. These checks use the same feed for Orka Cloud and self-hosted accounts.

## Build and promote a release

The [macOS build workflow](../.github/workflows/release.yml) produces a notarized DMG with one app and `Orka-update.zip` with the same stapled `Orka.app`. The updater is signed inside the bundle. The launcher provisions an independently signed copy under Application Support so it can keep running while Orka’s bundle is replaced. A newer embedded updater replaces an older installed helper after signature and trust configuration checks. Changes to the updater protocol, public key, or feed location require a compatible bootstrap release.

1. Provision a dedicated Ed25519 release policy signing key. Put the base64-encoded raw 32-byte public key in `ORKA_UPDATE_PUBLIC_KEY` in both protected environments. Set `ORKA_UPDATE_SIGNING_KEY` to the PKCS#8 PEM private key in `macos-update-publishing` only. Set its `APPLE_TEAM_ID` variable to the release signing team. The existing Apple signing credentials stay in `macos-signing`. Limit both environments to reviewed `main` workflows and keep access to the publishing key separate from Apple signing credentials.
2. Build the next version as **universal** and **notarized** from `main`. The release workflow uses Xcode 16.4 for the Intel and Apple Silicon launcher slices. Verify the DMG and the signed app with its nested updater, then attach the outputs to that version's GitHub desktop release. Publish the release for download. Keep each version and its update archive immutable.
3. Run **Publish macOS update policy** with **promote** and the version. Publish release notes on the matching GitHub release. The workflow verifies the notarized archive and its Apple team, then signs the policy and advances the `desktop-updates` branch. The default feed URL is `https://raw.githubusercontent.com/whysosaket/orka/desktop-updates/macos.json`. If `ORKA_UPDATE_FEED_URL` is overridden, the operator must serve the same signed policy at that URL. The feed works before sign-in and across managed and self-hosted instances.
4. The publishing workflow renews the 48-hour policy daily. Its environment must permit the scheduled `main` job to renew. If a reviewer gate is required for that environment, approve renewals before expiration. Monitor failed renewals and alert before the current policy expires.

## Withdraw a bad release

Run **Publish macOS update policy** with **withdraw** and the affected version. The withdrawal is permanent for that version. Optionally raise `minimum_version` when old builds must be excluded from installation and restore. The updater rechecks a fresh signed policy before an approved download can replace Orka. A Mac that has already observed a withdrawal remembers it across offline sessions. A Mac needs a successful feed refresh to learn about a new withdrawal.

Build the fix with a higher version and promote it. The updater can fetch it independently of the UI and sync process. Keep the old GitHub release for audit and mark it withdrawn in its release notes. Clients select from the signed desktop policy, including when the newest GitHub release is a server release.

## Data compatibility and acceptance

Increment [the desktop data epoch](../apps/mac/recovery/data-epoch) for a change that prevents the previous build from safely opening local data, retaining pending sync work, or using the supported server contract. The updater can install a forward version with a higher epoch and offers a local restore only within the same epoch. Test the old and new client against the same data and supported server versions before keeping the epoch unchanged.

LaunchServices starts the native desktop executable directly, preserving its process identity for the macOS menu bar. Before opening the workspace, the desktop holds the installation locks and asks the bundled recovery launcher to check cached withdrawal and crash state and start the health watcher. The legacy launcher entry point remains available for installed hooks and background commands; GUI launches through it return to LaunchServices rather than replacing a running process. The background updater records startup and exit health locally. For a regular update, it verifies the calling desktop process and rechecks the approved version and archive digest. The installer stages a signed full bundle on the installation volume, waits for foreground and background processes to release their shared runtime lock, and swaps the bundles atomically. An interruption leaves either the previous or the new complete bundle at the same path. The updater and application data live outside that swap.
